# Домены

[Русский](../ru/domains.md) | [English](../en/domains.md) | [简体中文](../zh-CN/domains.md)

## Можно вообще без своего домена?

Да. Для VLESS REALITY Vision и XHTTP REALITY можно подключаться к IP сервера.
В настройках REALITY используется имя внешнего TLS-сайта, но покупать этот
домен или управлять им не нужно. Доступность выбранного сайта нужно проверить.

Это относится и к прямому подключению, и к каскаду. Для трёх выходов за одним
входом не нужны три домена. Межсерверные REALITY-соединения тоже работают по IP.

Без своего домена можно передать ссылку или QR. Для удобной публичной
HTTPS-подписки в Lego выбираем вариант со своим доменом.

## Если нужен обычный TLS или подписка

Владелец покупает домен у любого регистратора или использует поддомен своего
существующего домена. Например, `vpn.example.com` и `sub.example.com`.
Lego не продаёт домены и не требует пользоваться нашим общим доменом.

Для VPN имя указывает на вход, не на зарубежный выход. Для подписки имя
указывает на сервер, который её публикует. Это может быть отдельный контрол.

Создайте A-запись для IPv4 и, только если настроен IPv6, AAAA-запись.
Для базового профиля TLS запись должна работать без CDN-прокси.
У Cloudflare это режим DNS only. Старая AAAA на другой сервер тоже мешает.

Подходят и динамические DNS-имена, если провайдер разрешает нужный сертификат
и имя стабильно доступно. Обязательной интеграции с конкретным DNS-провайдером нет.

## Что уже проверяет инструмент

```bash
lego-vpnctl topology plan installation.json
lego-vpnctl topology dns installation.json
```

План показывает, каким TLS-маршрутам нужны домены. DNS-проверка сравнивает
все A и AAAA с адресом ноды. Для ноды с двумя адресами можно указать её
DNS-имя в `address`, чтобы проверять оба.

Это проверка DNS, а не выпуск сертификата и не проверка доступности у оператора.
В текущем локальном инструменте сертификаты надо подготовить отдельно:
`/etc/ez-vpn-lego/certificates/ИМЯ/fullchain.pem` и `privkey.pem`.
Приватный ключ должен быть доступен Xray, но не остальным пользователям.
Автоматический выпуск и продление относятся к следующему этапу установщика.

## Если 443 уже занят

REALITY и обычный HTTPS нельзя просто запустить на одном IP и TCP-порту 443
двумя отдельными процессами. Новый поддомен этого не исправляет.

Для совмещённого сервера с REALITY на 443 предусмотрим HTTPS-подписку на другом
порту, например 8443. Другие варианты: отдельный IP или отдельный контрол с HTTPS 443.
Для XHTTP/TLS можно использовать общий HTTPS-вход с разными путями VPN и подписки;
этот шлюз ещё предстоит реализовать.

Мастер установки должен объяснить выбор до изменений и проверить занятые порты.
Никаких неожиданных изменений чужих сайтов или почтовых DNS-записей.

## Как жить дальше

Домен, DNS и продление регистрации остаются у владельца. Перенос между серверами
не должен требовать смены персональной ссылки подписки: меняется DNS или её
содержимое. Если домен перестал работать, остаётся аварийный экспорт ссылки через SSH.
Это требование к модульному релизу, а не уже готовая автоматизация.
